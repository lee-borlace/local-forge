# Security and data handling

LocalForge is an agent interface and guardrail, **not a sandbox or security boundary**. Native permissions, per-request catalogue filters and path checks reduce accidental actions; arbitrary project code, external MCPs, language servers, other plugins and user-approved commands can still act with the process's privileges. Use trusted repositories and isolate high-risk work in a restricted user/container/VM. Do not enable cloud or cross-machine routing for confidential projects.

Strict denies shell, Code Mode, subagents and external directory permissions through the native agent, reinforced by the plugin. Balanced allows shell with approval. Native reads/edits are checked against the active root, protected harness paths and obvious credential/config files; exact coverage depends on actual OpenCode permission events. Native grep/glob, Serena and extra tools may not invoke the same path checks. Secret heuristics are incomplete and not a data loss prevention system. Never expose untrusted MCP tools by adding them to `extraTools` without reviewing their permissions. Skills may be overridden by repository configuration; repository instruction and plugin precedence are controlled by OpenCode, not LocalForge.

`lf_verify` executes fixed recipes detected from existing files, requires approval unless its fingerprint is trusted and native rules allow. Fingerprints cover selected manifest contents, executable path and argv, not all transitive code or executable changes. Build/test can execute arbitrary code, read credentials from disk and use network. Environment filtering removes common secret variables for child processes, but does not isolate the OS or guarantee all secrets are removed. Windows command shims are restricted to simple fixed arguments. Timeout/cancellation on Windows may leave descendants; verify and clean up in live testing. No dependencies auto-installed by verification tools.

Shell fallback writes an exact command, reason, objective, root and session to local state. Human CLI review is required for one-time execution. Approval is not an instruction to run blindly. Check command and cwd. Pending requests expire after 24h; results and request records persist until manually removed. Human-approved shell can change anything accessible to the current user. Native shell may remain visible for balanced or off profiles. Do not treat hook-based restrictions as a protection against a malicious repository/plugin.

Local files under `<LF>/sessions/<repo-hash>/<session-hash>/`: `task.json` (agent notes), `status.json` (observed edits/checks/repeats), `metrics.jsonl` (local counts/timing), `outputs/<id>.txt` (bounded raw captured output, cleanup on session creation after retention). `<LF>/requests/<id>.json` plus transient `.lock` files contain commands/results. These may contain sensitive code or data. v0.3 backups contain only previously managed files, but old backups or user-modified files can contain sensitive data. Unix file modes are best effort; Windows ACLs inherit local user settings. No telemetry is transmitted by LocalForge. Upstream tools/model providers have their own network and data handling behaviour. Logs are not a full audit or success metric. Disable local metrics with `telemetry:false`.

## Provisioning trust

Installing any OpenCode server plugin authorizes code execution with the server user privileges. Review and pin the package source. LocalForge copies only manifest-listed native agents and helper files; existing unowned or modified files are preserved, and managed symlink/junction paths are rejected. The file manifest and locks are coordination mechanisms, not a security boundary against another same-user process. The installed helper is intentionally outside the plugin cache so users can approve an exact shell request or remove managed files even after package removal.

Runtime skills and Serena definitions are registered via public APIs and removed by OpenCode on unload. Native user configuration is not edited by LocalForge. External dependency installation requires explicit user command or opt-in package options; the selected fixed package manager and uv may download code and create caches. Serena runs as a local external process and can create project metadata or download language servers. The registered template forces individual tools, not its Python REPL. Existing server definitions are preserved and may have different permissions or behaviour. No shell fallback execution or package installation is exposed as an ordinary model-facing tool; strict profile is still not a sandbox.
