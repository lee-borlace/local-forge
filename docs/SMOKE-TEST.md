# Live validation checklist (not yet executed)

Use a disposable trusted repo and a known local model before real work. Never use a work repository or secrets for the first test.

1. From source, `node cli.js plan` and `npm pack --dry-run`; inspect exact payload. Push to a test GitHub repo, then `opencode plugin add github:lee-borlace/local-forge`. Start OpenCode in a disposable repository; confirm the package loads and `OC/agents/` and `LF/helper/` appear. Check `/localforge-status` and `/localforge-doctor`; restart if agents do not appear. Verify no duplicate plugin or JSONC mutation beyond OpenCode’s own package entry. If Serena is absent, use `/localforge-setup-serena` and verify package-manager commands and explicit consent. Confirm v2, `opencode plugin list`, `/mcps` and runtime skill/tool presence. Check logs for setup failures.
2. Open disposable repository A with a long source file, select `localforge-strict` and your local model. Inspect model-visible tools: no `shell`, `execute`, `subagent`; native read/edit/grep/glob and Serena symbol tools present. Ask for symbol outline then one method. Ask explicitly for full read; inspect tool input and ensure limit is capped (120 by default) and offsets work. If missing, validate real ToolExecuteBefore event schema and fix hook using public API. Do not assume hook tests prove this.
2a. Log or inspect `event.model` in the `context` hook for your model and confirm `limit.input`/`limit.context` is present. If it is, `read` should clamp near `window/8/12` lines (about 42 for a 4096 input limit); if it is absent, the static ceilings apply and this feature does nothing.
3. Change one file via native edit; ensure `lf_finish` now reports no verification since edit. Check native edit event shape and whether write/patch also invalidate. Use failing then passing test; inspect exit codes. Confirm a subsequent edit invalidates previous pass. Do not trust a ready flag as sole completion evidence.
4. Ask for `git status`, check tool selection. Request an unusual command; verify it does not run until `node "$HOME/.localforge/helper/cli.js" shell <id>` and explicit yes. Verify known simple alternatives are rejected. Test native denial and an external path in disposable environment. Inspect approvals; trust a recipe only after review, confirm denies still win.
5. Open repository B concurrently. Verify each Serena process resolves its own directory and task/output state is isolated. Test unsupported language and absent tools; native bounded search fallback should work.
6. Switch to balanced then ordinary build agent with a frontier model. Check shell policy and tool list restore appropriately; native Serena remains registered. Check original default agent/provider are unchanged. If using profile matching without named agent, inspect Code Mode behaviour before relying on it.
7. Test actual Windows executable discovery, WinGet bootstrap/PATH refresh, uv installation and Node package-manager command shims, timeout and process cleanup. Test Unity candidate with existing editor path (`LOCALFORGE_UNITY_EDITOR`) and examine test result, not just exit code. Optional DCP/RTK: enable one at a time, repeat and compare behaviour; disable if conflicts.
8. Test package update and restart, concurrent first loads, user-modified agent conflict, `/localforge-repair`, then `opencode plugin remove github:lee-borlace/local-forge`. Check skills/MCP disappear on unload. Close OpenCode and run helper `cleanup`; confirm unchanged owned files disappear, modified/unowned files survive, user config and target repos remain untouched. Review backups and external packages.
9. Stacked install: with another OpenCode setup that has a global `"*": "deny"` permission, confirm `lf_*` calls succeed under `localforge-strict`, that other plugins' tools are hidden only as documented, and that no subagent from the other setup gives the strict agent shell access.

Only after this can compatibility be claimed for the tested version/platform. For effectiveness, compare baseline and enhanced OpenCode on identical disposable tasks/model/settings, assessing correctness with hidden regression tests, context, manual approvals, and shell requests. No automated live benchmark is bundled.
